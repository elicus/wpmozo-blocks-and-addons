# Pattern Library decisions (approved only)

Each entry: ID, date approved, decision, reason. Proposed or open items are not listed here; they live in [handoff.md](handoff.md) (open questions) and [roadmap.md](roadmap.md) (proposed stages from the 2026-11-05 audit). An approved change to a decision is added as a new entry that names the entry it replaces; old entries are never rewritten. The full reasoning and alternatives are in [architecture-readiness-review.md](architecture-readiness-review.md) (section in brackets). Licence and Pro-security details are recorded in the private Pro repository.

## Implementation decisions (within the approved architecture)

| ID | Date | Decision | Reason |
|---|---|---|---|
| PL-D12 | 2026-11-03 | **Restricted-HTML detection (implements PL-D05):** per pattern, compare a structural fingerprint (blocks and comment attributes, every tag with its attribute names and decoded values) of the content before and after `wp_kses( $content, 'post' )`. No hand-maintained block list | Measured on 108 WPMozo blocks (WordPress 6.8.11 and 7.1.3): 44 change under the Author save filter, 43 then fail validation. A "blocks that save `<style>`" list would miss Ajax Search, Bar Chart and Pie Chart. A byte comparison would wrongly lock core images (`/>` vs ` />`). The fingerprint matches the measured list exactly ([security.md](security.md)) |
| PL-D13 | 2026-11-03 | **Validator rules** as listed in [security.md](security.md):<ul><li>HTML checked tag by tag with WordPress's HTML Tag Processor (decoded attribute values);</li><li>exceptions only for the exact no-op `javascript:void(0)` that WPMozo buttons save and for microdata `<meta itemprop>`;</li><li>text attributes starting with `Data:` are rejected (documented strictness).</li></ul> | Regex over raw text missed entity- and tab-encoded `javascript:`, and rejected harmless text. All 67 Lite blocks' default markup passes; 13 attack probes are rejected |
| PL-D14 | 2026-11-03 | **Analysis cache** (key extended by PL-D23):<ul><li>one transient per source (one-week expiry);</li><li>key = source id, source version, central-map modification times;</li><li>entries reused only while revision and `content.php` modification time are unchanged;</li><li>no other stored data.</li></ul> | Catalog requests stay fast without trusting authored "blocks used" lists. Updates and edits invalidate automatically |
| PL-D15 | 2026-11-03 | **Placeholder block** `wpmozo/pattern-library`:<ul><li>always registered;</li><li>saves an empty comment and renders nothing;</li><li>hidden from the inserter in `block.json`; the library script shows it with a `blocks.registerBlockType` filter plus `reapplyBlockTypeFilters()`;</li><li>no automatic opening on insert;</li><li>rejected inside pattern content.</li></ul> | Saved placeholders must never break, even with the library off or in other editors. The library script already loads only where the library can be used, so the inserter rule needs no second copy of those conditions. Opening on insert can't tell a new block from a saved one |
| PL-D16 | 2026-11-03 | **Library switch saving:** `panel-library.js` adds the switch to the settings panel's existing save request with `jQuery.ajaxPrefilter`. The panel script and the save handler are unchanged | `panel.min.js` has no source in the repository, so editing it is unsafe. The save handler already stores any submitted option key. One request, one Save button |

| PL-D18 | 2026-11-04 | **Patterns are authored on the minimum supported WordPress (6.8).** The importer accepts raw attributes that a block's deprecations declare. | Newer WordPress migrates older block markup through deprecations, but older WordPress can't read newer markup. Without the importer rule, 7.1 refused valid 6.8 content |
| PL-D19 | 2026-11-04 | **Export removes attributes derived from the editor ID** (`ID`, `wrapStyle`) and fails if any client ID remains. | They are site- and insert-specific. The importer and the blocks recreate them. `wrapStyle` also holds braces, which the validator rejects |
| PL-D20 | 2026-11-04 | **Pilot content:**<ul><li>2 free (hero, pricing) + 2 Pro (features, process), temporary designs;</li><li>WPMozo blocks are the featured elements;</li><li>CTAs use core Buttons;</li><li>blocks with front-end defects are avoided;</li><li>fonts follow the theme, colours come from one token set;</li><li>original local illustrations.</li></ul> | Owner asked for production-quality temporary designs without supplying them (2026-11-04). The block issues are listed in [testing.md](testing.md) |
| PL-D21 | 2026-11-04 | **Temporary Lite-to-Pro card link** on the reserved `example.com` domain, marked in `data/links.php`. | Owner: use a clearly marked temporary value until the destination is confirmed; never invent a production URL. Replacing it is a release blocker |

| PL-D22 | 2026-11-04 | **Editability is part of the quality gate:** every block type's Inspector must render on all its tabs, and inline text edits must survive save, reload and the front end. It runs on a separate page, so previews stay clean | Owner asked for full Gutenberg editability, not only insertion. A generic check covers replacement and future patterns without pattern-specific scripts |

| ID | Date | Decision | Reason |
|---|---|---|---|
| PL-D23 | 2026-11-05 | **Analysis cache key (extends PL-D14; R1).** Each source's key is its id plus one environment stamp: the Lite version, the validator rules version (`Mozo_Bna_Library_Validator::RULES_VERSION`), the WordPress version, the HTML allowed in posts, and every registered source's version and central-map modification times. Revision and `content.php` time still decide per pattern | Audit KI-01: a Lite update, a WordPress update or a change to another source's maps (Pro patterns use Lite icons) left the catalog wrong for up to a week. Re-analysing a few patterns after any change costs little |
| PL-D24 | 2026-11-05 | **Library files are loaded through one safe include (R1).** `Mozo_Bna_Library_Registry::safe_include()` catches any `Throwable` (parse errors included): a broken `pattern.php` skips that pattern, a broken `content.php` makes it unavailable, a broken map fails closed for the tokens it holds. Each is reported in the catalog's `issues` (administrators only). Anything a file prints is discarded and reported | Audit KI-02: one malformed add-on file took the whole library down, free patterns included. Pro must never break Lite |
| PL-D25 | 2026-11-05 | **A pattern that uses a Lite map key the installed Lite lacks is `unavailable: lite_outdated` (R1),** not `invalid_content`, when the pattern belongs to another source. A missing key in Lite's own pattern stays `invalid_content` (an authoring error) | Audit KI-03: the user couldn't tell that updating Lite fixes it. Lite's released keys never disappear, so a missing one means an older Lite |
| PL-D26 | 2026-11-05 | **The content route analyses the pattern afresh (R1),** ignoring the cache, refuses it by the fresh `requires_unfiltered_html` result, and stores the fresh result for the catalog | Audit R-07 and consistency: the catalog and the content route must give the same answer, and delivery must never rely on a cached safety result |
| PL-D27 | 2026-11-06 | **Every Lite surface add-ons use is frozen and machine-checked, without a new interface layer (R4).** The inventory and its classification (contract, intended, shared data model, accidental) are [registry-and-contract.md](registry-and-contract.md) section 4; `tools/pattern-library/tests/lib/surface.cjs` is the same list and the `contract` suite checks it, including what Pro uses and what Lite reads from Pro. No rename or replacement layer for the accidental surfaces; their saved forms (the placeholder image URL, the content wrapper's markup) are frozen as they are | Owner-approved R4 scope. Released Pro versions already rely on these surfaces, so moving them would need the deprecation rules anyway; a check that fails on any change protects both plugins without a rewrite |
| PL-D28 | 2026-11-06 | **Lite is the only owner of the shared vendor handles, Chart.js included (R4, PKI-07 option B′).** Lite registers them on `init`; add-ons reference them and never register a handle under a Lite name. Pro dropped its own registration of `wpmozo-blocks-and-addons-chartjs-script`, which pointed to a file Pro never contained | Two plugins registering one handle with different files means whichever runs first wins (R-14). Lite registers the handle with Chart.js 4.5.1 since `6ffb99f`, for Pro's charts; one owner keeps the file and its version in one place. With Lite 1.8.0 or older, Pro's charts still can't draw; the guard that would avoid the error belongs to the block (a separate task, [known-issues.md](known-issues.md)) |
| PL-D29 | 2026-11-06 | **Pattern Library work never modifies block code** (`src/blocks/`, any block folder, per-block template folders) in Lite or Pro. Block issues it finds are recorded in `known-issues.md` (block, issue, cause, impact, recommended fix) for a separate developer after the Pattern Library is complete | Owner rule, given before R4: finish the Pattern Library without unrelated block changes. Each commit is checked for block paths; mutation tests run on throwaway copies outside both repositories |
| PL-D30 | 2026-11-06 | **Lite's editor stylesheet is enqueued on `enqueue_block_assets`, only when `is_admin()` (R6, KI-05).** WordPress fires that action for the editor page and again for the editor canvas, so the stylesheet reaches both on its own; the front end never loads it. It is no longer enqueued on `enqueue_block_editor_assets` | WordPress 6.8 and 7.1 copied the old enqueue into the canvas with a warning that they may stop doing so; that would remove Lite and Pro block styling from the canvas. Verified with and without the canvas iframe, with a classic meta box, and on the front end (testing.md R6). Other R6 items (R-02, R-03, R-11 and the block follow-ups) are checks or records only, because they would change block code (PL-D29) |

**Process (approved 2026-11-03):**
- Lite Pattern Library work goes on `dev/sunil`; Pro Pattern Library work on `release/pattern-lib`.
- Approved work is committed and pushed automatically in small verified units, code and docs in separate commits. No force-push, reset or merge of other branches.
