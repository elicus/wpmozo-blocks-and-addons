# Pattern authoring

How to create, change and replace Pattern Library patterns. It covers the files, the tools in `tools/pattern-library/`, and the rules learned while building the pilot (LPL-T, 2026-11-04). The contract itself (sources, metadata schema, tokens) is in [registry-and-contract.md](registry-and-contract.md).

## Where everything lives

Each source has one library folder: Lite's is `includes/library/`, and the Pro plugin has its own with the same layout.

| Path (in the source's library folder) | What | Shipped |
|---|---|---|
| `patterns/<slug>/pattern.php` | Metadata: title, category, access, thumbnail, revision… | Yes |
| `patterns/<slug>/content.php` | Block markup with tokens, generated by `build-content.php` | Yes |
| `previews/<slug>.<revision>.webp` | Card thumbnail, 800 × 600 | Yes |
| `previews/<slug>.<revision>-full.webp` | Large preview, 1200 px wide | Yes |
| `media/<key>.<revision>.webp` | Images used inside pattern content | Yes (permanent once released) |
| `data/media.php` | Media map: key → file, size, reference alt text | Yes |
| Lite `data/links.php`, `icons.php`, `demo-text.php` | Shared maps for links, icon classes and repeated demo text (all sources use them) | Yes |
| Lite `data/categories.php`, `tags.php` | Category and tag vocabulary | Yes |
| `tools/pattern-library/` (each plugin's repository) | Authoring tools (Lite) and illustration sources (`art/`) | No |

Thumbnails and content images are separate files (CDN requirement §3): a thumbnail never contains or leads to pattern content.

## Tokens: the replaceable values

`content.php` never contains a site URL or a value that may change centrally. Instead it contains tokens, resolved on the server when the pattern is inserted:

| In the design | In `content.php` | Value from |
|---|---|---|
| An image under `<plugin>/includes/library/media/` | `{{wpmozo:media:<source>/<key>}}` | The source's `data/media.php` + the asset resolver |
| A link set to `#wpmozo-link-<key>` | `{{wpmozo:link:lite/<key>}}` | Lite `data/links.php` (demo links are `#`) |
| An icon class listed in Lite `data/icons.php` | `{{wpmozo:icon:lite/<key>}}` | Lite `data/icons.php` |
| Text listed in Lite `data/demo-text.php` (for example "Northwind") | `{{wpmozo:text:lite/<key>}}` | Lite `data/demo-text.php` |

Changing a map value changes every pattern that uses it, for future insertions only. Content that users have already inserted keeps the old values.

## Workflow

Requirements: Node with this plugin's `node_modules` (Playwright, Google Chrome), PHP CLI, and `cwebp` (macOS: `brew install webp`).

1. **Development site.** Use the **minimum supported WordPress (6.8)**, with Lite (and Pro for Pro patterns) active, the library on, and a Pro licence activated for Pro patterns.
   - Newer WordPress versions migrate older block markup (for example 7.1 moves Heading `textAlign` into `style`), but older versions can't read newer markup. The importer accepts attributes that a block's deprecations declare ([import-workflow.md](import-workflow.md)).
2. **Design the section** in the block editor as one top-level block, normally a full-width Group.
   - Use local images from the media folder, demo links `#wpmozo-link-<key>`, and icon classes from the icon map.
   - Save it, and let the editor settle before saving. Some blocks write attributes when they mount (IDs, Timeline item flags, Advanced Counter markup).
3. **Export:** `node tools/pattern-library/export.cjs <site-url> <post-id> <out.html> [--storage-state=<file>]`.
   - Every block is rebuilt.
   - Attributes derived from the editor ID (`ID`, `wrapStyle`) are removed; the importer and the blocks recreate them.
   - The export stops if any client ID remains.
4. **Build the content file:** `php tools/pattern-library/build-content.php --source=<lite|pro> --library=<source library folder> --lite-library=<Lite includes/library> --slug=<slug> --in=<out.html>`.
   - It replaces values with tokens and checks the round trip.
   - It stops on any value it can't map (an image outside the media maps, a site URL, an unknown link key).
5. **Write `pattern.php`** (schema 1; see the existing patterns). Set `revision`, `since` and, for Pro, `published`.
6. **Gate and previews:** `node tools/pattern-library/gate.cjs <site-url> <source/slug>… --log=<file.json> --previews=lite:<Lite library>,pro:<Pro library>`.
   - It writes both preview images, named with the pattern's `revision`.
   - Put the full preview's height into `pattern.php`.
7. **Run the gate again on the latest WordPress** (without `--previews`), and check roles: Authors and Contributors lack `unfiltered_html`, so patterns whose blocks save `<style>` are unavailable to them (policy D3; the catalog says why).

## Quality gate (readiness review §0.6)
`gate.cjs` checks:
- available in the catalog, with no issues;
- inserts through the library window;
- valid blocks, still valid after saving and reloading;
- uses at least one WPMozo block;
- at 1440, 768 and 360 px: no horizontal overflow, images load and have alt text, no page errors (the page is scrolled through first, so scroll animations run).

Each run writes a log, never overwriting an earlier one. Check headings and the design visually as well: the gate only lists the headings, and design quality needs a person.

## Changing or replacing a pattern
| Change | What to do |
|---|---|
| Copy or layout | Edit the design page, export, build content again, raise `revision`, recapture previews |
| A content image | Add `media/<key>.<revision+1>.webp` and point the media map entry at it. Never delete or rename a released image: saved pages use it |
| A demo link, icon or repeated text | Edit the map value; every pattern that uses it follows |
| The thumbnail only | Raise `revision`, run the gate with `--previews`, update `pattern.php` |
| Retire a pattern | Set `status` to `deprecated` (optionally `replaced_by`); never reuse the slug |
| A new pattern | New folder and slug; the library, importer and REST routes need no change |

Illustration sources (`tools/pattern-library/art/*.svg`) render with `node tools/pattern-library/render-art.cjs <svg> <media/key.revision.webp>`.

## Pilot design tokens (2026-11-04)
The pilot patterns share one set of values, so they look like one family.

| Token | Value |
|---|---|
| Ink (headings) | `#0f172a` |
| Body text | `#475569` |
| Muted | `#64748b` |
| Lines | `#e2e8f0` |
| Subtle background | `#f8fafc` |
| Brand | `#4f46e5` (hover `#4338ca`) |
| Brand soft | `#eef2ff` |
| Accent | `#f59e0b` |
| Dark band | `#0b1120` |
| Radius | 12 px (controls), 20 px (cards) |
| Section padding | `clamp(4rem, 8vw, 7rem)` vertical, `clamp(1.25rem, 4vw, 2rem)` sides |
| Content width | 1200 px (header text 760 px) |
| Type scale | display `clamp(2.5rem, 5.2vw, 4.25rem)`; h2 `clamp(2rem, 3.6vw, 2.875rem)`; lead `clamp(1.0625rem, 1.4vw, 1.1875rem)` |

Fonts are never set: they follow the theme. Patterns set their own colours, and users can change every colour after inserting.

## Rules learned from the pilot
- **CTAs use core Buttons.** WPMozo Advanced Button saves `href="javascript:void(0)"` and never outputs its URL, so its links don't work on the front end.
- **Check every block on a page without jQuery.** Several block scripts use jQuery without declaring it. On a block-theme page where nothing else loads jQuery, they fail; the gate's page-error check catches this.
- **Block attribute types matter.** A value of the wrong type is dropped when saving (for example Pricing Table's `price` is a string).
- **Prefer blocks without attributes that hold braces.** The validator rejects `{` and `}` in any attribute value, because some blocks print attributes into `<style>`.
- **Images need alt text in the content.** Blocks that always write an empty `alt` aren't suitable for meaningful images.
- **Sections with a background colour can hide decorations** that a block draws with a negative `z-index`. Check visually.
